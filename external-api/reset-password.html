Reset Password — Panduan Integrasi untuk OMNI

Empat panggilan yang membawa satu UUID dari awal sampai akhir. Semuanya bisa dijalankan sekarang lewat curl atau Postman — tidak perlu halaman web, tidak perlu sesi login. Yang dibutuhkan cuma akses ke inbox email yang dipakai.

Menanggapi masukan tim Omni. Kalau kamu sudah mulai memetakan respons kami, tiga hal ini mengubah apa yang perlu dibaca:

  • Langkah 1 sekarang selalu 200. Email tidak terdaftar (dulu 404) dan pengiriman gagal (dulu 500) kini ikut 200, dibedakan lewat data.is_email_matched dan data.send_success. Jeda 1 menit juga 200, ditandai data.is_rate_limited.
  • Langkah 1 mengembalikan data. Dulu hanya message. Kini membawa request_id dan reset_link_expires_in.
  • Langkah 4 punya tiga kode error baru: PASSWORD_POLICY_VIOLATION, SAME_PASSWORD, dan PASSWORD_HISTORY_MATCH, terbaca di field error_code.

Kode error dikirim di tingkat atas sebagai error_code, bukan di dalam result — amplop message + data dipakai seluruh API kami, jadi kami tidak mengubahnya untuk satu endpoint. Isinya sama, tinggal dipetakan.

01 Siapkan

Dua nilai, satu prasyarat. Setelah ini bisa langsung jalan.

API key

Semua endpoint /external dijaga header X-API-KEY. Nilainya harus sama persis dengan AUTH_OMNI_API_KEY (atau AUTH_ARCHI_API_KEY) di env backend — minta ke tim backend, jangan disalin ke dokumen publik.

X-API-KEY <nilai AUTH_OMNI_API_KEY>

Key ini membuka seluruh permukaan /external — bukan cuma reset password — dan dipakai bersama, bukan key khusus per tim. Aman untuk curl dan pengujian, tapi jangan sampai ikut ter-commit ke repo publik atau tertanam di bundle yang dikirim ke browser.

Versi yang dipakai

Alur OTP di dokumen ini sudah masuk development lewat PR #119. Pastikan environment yang kamu tembak menjalankan build dari development setelah PR itu — ter-merge dan ter-deploy adalah dua hal berbeda.

Penanda cepat: kalau email yang masuk tidak memuat kode 6 digit, atau tautannya mengarah ke yourfrontend.com, berarti environment itu masih versi lama. Itu bukan salah request kamu — minta tim backend memperbarui build-nya.

Akses ke inbox

Alurnya menuntut dua nilai yang cuma dikirim lewat email: token rst dan kode OTP 6 digit. Tidak ada endpoint untuk membacanya, jadi pakai alamat email yang inbox-nya bisa kamu buka.

Email yang dipakai harus sudah terdaftar sebagai user. Alamat yang tidak dikenal tetap dibalas 200, dengan data.is_email_matched: false — bukan 404.

02 Empat Endpoint

Urutan ini mengikat. Langkah 4 akan ditolak kalau langkah 3 dilewati — itu memang penjaganya. Semua respons memakai amplop yang sama: message, lalu data atau errors bila ada.

1

Kirim email berisi tautan + OTP

POST/api/v1/external/passwords/reset/initiate

Satu email membawa dua hal sekaligus: tautan yang mengandung token, dan kode 6 digit di badan emailnya. Selalu membalas 200 — hasilnya dibaca dari data, bukan dari status.

Request
{
  "email": "user@example.com"
}
200 — terkirim
{
  "message": "Password reset email sent successfully",
  "data": {
    "is_email_matched": true,
    "send_success": true,
    "request_id": "019ffa7a-b1d3-7718-b98e-ad2b3148ce0d",
    "reset_link_expires_in": 1800
  }
}
200 — email tidak terdaftar
{
  "message": "Email not registered",
  "data": {
    "is_email_matched": false,
    "send_success": false,
    "request_id": "019ffa7a-e089-..."
  }
}
200 — pengiriman gagal
{
  "message": "Email matched but sending failed",
  "data": {
    "is_email_matched": true,
    "send_success": false,
    "request_id": "019ffa7a-c97a-..."
  }
}
200 — diminta lagi dalam 1 menit
{
  "message": "Too many reset password requests",
  "data": {
    "is_email_matched": true,
    "send_success": false,
    "is_rate_limited": true,
    "request_id": "019ffa7a-c6ba-..."
  }
}
Catatan
// is_rate_limited hanya muncul saat kena jeda.
// reset_link_expires_in (detik) hanya muncul saat
// email benar-benar terkirim.
//
// request_id sama dengan header
// X-Hyperscal-Request-Id. Kirim header itu
// dengan id kalian sendiri, dan nilainya
// diteruskan apa adanya ke respons + log kami.
2

Cek token masih hidup

GET/api/v1/external/passwords/reset/validate?token=<rst>

Opsional — tidak memengaruhi langkah berikutnya. Gunanya memastikan token belum kedaluwarsa sebelum meneruskan alur.

Request
// tanpa body, token di query string
?token=16d46b2e-6306-4eb0-91a1-a1494d1e83c1
200 OK
{
  "message": "Password reset token is valid"
}
3

Validasi OTP

POST/api/v1/external/otp/validate

reference_token diisi nilai rst yang sama. OTP memang sengaja memakai UUID token reset, jadi tidak ada nilai kedua yang perlu dibawa.

Request
{
  "reference_token": "16d46b2e-...-a1494d1e83c1",
  "otp": "483920"
}
200 OK
{
  "message": "OTP validated successfully",
  "data": {
    "otp_verified": true,
    "reference_token": "16d46b2e-...",
    "remaining_attempt": 5,
    "remaining_daily_attempt": 5
  }
}
4

Pasang kata sandi baru

POST/api/v1/external/passwords/reset

Nilai rst yang sama lagi, kali ini dengan nama field reset_token. Setelah berhasil, token dan OTP dihapus — jadi request yang sama tidak bisa diulang.

Request
{
  "reset_token": "16d46b2e-...-a1494d1e83c1",
  "password": "Gunung#Salak92"
}
200 OK
{
  "message": "Password reset successfully"
}
400 — kata sandi tidak memenuhi syarat
{
  "message": "the new password does not meet the
              password policy requirements",
  "error_code": "PASSWORD_POLICY_VIOLATION"
}
409 — sama dengan kata sandi sekarang
{
  "message": "the new password must be different
              from your current password",
  "error_code": "SAME_PASSWORD"
}
409 — pernah dipakai belakangan ini
{
  "message": "the new password matches one of your
              last five passwords, please choose
              a different password",
  "error_code": "PASSWORD_HISTORY_MATCH"
}
Catatan
// Ketiga penolakan ini TIDAK menghanguskan
// token maupun OTP -- pengguna bisa langsung
// mencoba kata sandi lain tanpa mengulang
// dari email.
//
// Urutan pemeriksaannya: kebijakan dulu, baru
// pemakaian ulang.

03 Jalankan Berurutan

Ganti BASE, KEY, dan EMAIL, sisanya sudah siap pakai. Jalankan dari atas ke bawah.

Siapkan
BASE="http://localhost:8080/api/v1/external"
KEY="<nilai AUTH_OMNI_API_KEY>"
EMAIL="user@example.com"
1 — minta email reset
curl -s -X POST "$BASE/passwords/reset/initiate" \
  -H "X-API-KEY: $KEY" \
  -H "Content-Type: application/json" \
  -d "{\"email\":\"$EMAIL\"}"

# Selalu 200. Periksa data.send_success -- kalau false,
# emailnya tidak terkirim dan tidak ada gunanya menunggu inbox.
# data.is_email_matched false berarti alamatnya tidak terdaftar.
Ambil dua nilai dari email
# Buka inbox. Emailnya memuat sebuah tautan dan sebuah kode.
#
# Dari tautannya, ambil bagian setelah ?rst= saja:
#   https://.../auth/forgot-password?rst=16d46b2e-6306-4eb0-91a1-a1494d1e83c1
#                                         ^-------------- ini yang dipakai --------------^
#
# Halaman yang dituju tautan itu tidak perlu ada. Kamu memanggil
# API langsung, jadi cukup nilai rst-nya.

RST="16d46b2e-6306-4eb0-91a1-a1494d1e83c1"
OTP="483920"   # kode 6 digit di badan email
2 — pastikan token masih hidup
curl -s "$BASE/passwords/reset/validate?token=$RST" \
  -H "X-API-KEY: $KEY"

# Harapan: "Password reset token is valid"
3 — validasi OTP
curl -s -X POST "$BASE/otp/validate" \
  -H "X-API-KEY: $KEY" \
  -H "Content-Type: application/json" \
  -d "{\"reference_token\":\"$RST\",\"otp\":\"$OTP\"}"

# Periksa data.otp_verified — harus true.
# Kalau false, kodenya salah; statusnya tetap 200.
4 — pasang kata sandi baru
curl -s -X POST "$BASE/passwords/reset" \
  -H "X-API-KEY: $KEY" \
  -H "Content-Type: application/json" \
  -d "{\"reset_token\":\"$RST\",\"password\":\"Gunung#Salak92\"}"

# Harapan: "Password reset successfully"
#
# Kalau ditolak, baca error_code:
#   400 PASSWORD_POLICY_VIOLATION -- kata sandinya terlalu lemah
#   409 SAME_PASSWORD            -- sama dengan yang sekarang
#   409 PASSWORD_HISTORY_MATCH   -- salah satu dari 5 terakhir
# Token tetap hidup, jadi tinggal ulangi dengan kata sandi lain.
5 — buktikan penjaganya bekerja
# Ulangi langkah 1 untuk dapat RST baru, lalu LEWATI langkah 3
# dan langsung tembak langkah 4:

curl -s -X POST "$BASE/passwords/reset" \
  -H "X-API-KEY: $KEY" \
  -H "Content-Type: application/json" \
  -d "{\"reset_token\":\"$RST_BARU\",\"password\":\"Gunung#Salak92\"}"

# Harapan: 400 "verification code has not been verified"
# Kalau ini justru berhasil, ada yang salah — laporkan ke tim backend.

05 Jebakan

Hal-hal yang tidak terbaca dari nama endpoint-nya, dan paling sering bikin waktu terbuang.

OTP salah tetap balas 200, bukan error

Kode yang salah membalas 200 OK dengan data.otp_verified: false. Kalau logika kamu cuma memeriksa status HTTP, alurnya akan lanjut ke langkah 4 padahal OTP belum tervalidasi — lalu gagal dengan pesan yang kelihatannya tidak nyambung.

Periksa boolean data.otp_verified, bukan status code. data.remaining_attempt menunjukkan sisa percobaan; batasnya 5 per kode.

Key di object errors memakai huruf besar

Validasi gagal membalas 422 dengan key mengikuti nama field Go, bukan nama JSON-nya: Password, ResetToken, Email — bukan password atau reset_token.

Parser yang mencari errors.password akan selalu dapat undefined.

Langkah 1 tidak pernah gagal lewat status HTTP

Email tidak terdaftar, pengiriman ditolak penyedia, dan permintaan berulang dalam 1 menit — ketiganya membalas 200. Yang membedakan hanya message dan tiga boolean di data.

Jangan simpulkan berhasil dari status 200 saja. Alur yang benar: send_success true berarti email sudah keluar; false dengan is_rate_limited true berarti tautan sebelumnya masih hidup dan sudah ada di inbox pengguna — pesan yang tepat bukan "gagal, coba lagi" melainkan "cek inbox kamu".

Kata sandi baru bisa ditolak tiga cara berbeda

Langkah 4 memeriksa kekuatan kata sandi, lalu memeriksa apakah pernah dipakai. Ketiga penolakannya membawa error_code yang stabil — pakai itu untuk bercabang, bukan teks message, yang sewaktu-waktu bisa diubah kalimatnya.

Penting: penolakan ini tidak menghanguskan token. Pengguna yang salah tiga kali tetap bisa mencoba lagi tanpa meminta email baru.

Tautan dan OTP mati bersamaan

Keduanya memakai satu masa berlaku yang sama dari config backend, dan lahir dari UUID yang sama. Tidak ada skenario "token masih hidup tapi OTP sudah mati" atau sebaliknya.

Kalau salah satu kedaluwarsa, ulangi dari langkah 1 untuk mendapat pasangan yang baru.

Jangan pakai PUT /passwords atau POST /users/password

Dua rute itu ada di router dan kelihatan sah, tapi menjalankan handler yang sama persis dengan langkah 4 — termasuk keharusan punya token reset. Keduanya bukan endpoint ganti kata sandi untuk pengguna yang sudah login; padanan itu belum ada di /external.

Kalau kamu memilih salah satunya, hasilnya tetap benar sekarang, tapi integrasimu akan rusak saat rute duplikat itu dirapikan. Pakai POST /passwords/reset.

06 Aturan Kata Sandi

Divalidasi di backend pada langkah 4, dalam dua tahap.

Kekuatan — ditolak dengan PASSWORD_POLICY_VIOLATION (400)

  • Minimal 12 karakter
  • Ada huruf besar dan huruf kecil
  • Ada angka
  • Ada karakter spesial
  • Tidak boleh mengandung spasi, tab, atau spasi bentuk lain

Pemakaian ulang — ditolak dengan 409

  • Sama dengan kata sandi yang sedang dipakai → SAME_PASSWORD
  • Sama dengan salah satu dari 5 kata sandi terakhir → PASSWORD_HISTORY_MATCH
Riwayat pengguna lama dimulai dari kosong

Kata sandi lama tidak pernah disimpan sebelum perubahan ini, jadi tiap pengguna yang sudah ada mulai dengan riwayat berisi satu entri. Aturan "5 terakhir" baru benar-benar mengikat setelah mereka berganti kata sandi beberapa kali.

Jadi kalau kalian menguji dengan akun lama dan PASSWORD_HISTORY_MATCH tidak pernah muncul, itu bukan berarti aturannya tidak jalan — riwayatnya memang belum terisi.

07 Ringkasan Respons

StatusKapan munculArtinya
200 Langkah 1 — keempat hasilnya Baca data.is_email_matched, data.send_success, data.is_rate_limited
200 Langkah 3 — termasuk saat OTP salah Periksa data.otp_verified, bukan status
400 Kata sandi tidak memenuhi syarat error_code: PASSWORD_POLICY_VIOLATION
400 Token kedaluwarsa, tipe token salah, atau OTP belum divalidasi Tanpa error_code; baca message
409 Kata sandi sama dengan yang sekarang error_code: SAME_PASSWORD
409 Kata sandi pernah dipakai belakangan ini error_code: PASSWORD_HISTORY_MATCH
422 Bentuk request tidak valid (mis. token bukan UUID) Baca errors dengan key huruf besar: ResetToken
401 X-API-KEY hilang atau salah Masalah header, bukan isi request

Disusun dari kode di development per PR #119. Bentuk request, response, dan pesan error di atas diambil langsung dari sumbernya, bukan dari spesifikasi terpisah — jadi kalau ada yang tidak cocok saat dicoba, itu temuan yang layak dilaporkan.
